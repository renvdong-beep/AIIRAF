## 一、技术领域

本发明属于机器人软件开发与部署交叉领域，具体涉及一种机器人应用的**开发范式与交付方法**：应用开发者以**组合技能（Skill）**的方式描述机器人作业，框架负责把这些技能组合**适配到特定的板卡（含 Hypervisor 多虚拟机分域构型）与特定的操作系统/发行版/架构**上运行，并保证同一份组合语义在仿真环境与边缘板级目标上一致、可复现、可审计。

## 二、背景技术

### 2.1 现有做法与本项目的目标做法

**现有典型做法**：应用开发者直接面向某一块板 + 某一个 OS + 某一套中间件（ROS 2 topic/action、厂家 SDK、现场总线接口）开发。换板、换 OS、换机型 ⇒ 改业务代码；"能不能跑起来"取决于开发者是否恰好熟悉该板的 BSP、Python 版本、glibc、平台标签与依赖链。

**本项目目标做法**：应用开发者只组合技能（`pick_object`、`place_object`、`navigate`、`stand`、`stop` …），只填本体与板级声明；机型差异、板级差异、中间件差异全部下沉到声明文件与适配层。同一份技能组合在 MuJoCo 仿真、容器兼容档与边缘板级目标上使用**同一技能包集合与同一公开接口语义**执行。

### 2.2 现有技术格局

| 现有技术 | 覆盖 | 未覆盖（本发明的切入点） |
|---|---|---|
| ROS 2 / MoveIt 2 / Nav2 / ros2_control | 规划、控制、动作接口 | 技能包的标准合约、能力声明与实现的一致性校验、跨板/跨 OS 声明与交付 |
| 厂家 SDK 与官方仿真栈（如宇树 `unitree_mujoco` / `unitree_ros2`） | 单机型低层控制与消息 | 跨机型/跨板的技能组合语义；板级未知字段的显式拒绝 |
| 声明式硬件资源平台（如 Viam） | 资源声明、统一 API、云侧部署与诊断 | 板级/OS 目标的**实测标签预检与失败关闭安装**；Hypervisor 多 VM 分域构型声明；技能组合的编译期校验 |
| 车队/场地调度（如 Open-RMF） | 多机任务分派 | 单机技能合约、能力契约、离线依赖与跨架构产物 |
| 学习策略/数据框架（如 LeRobot） | 策略与数据集接口 | 不是安全执行器，也不负责板级交付与能力声明 |
| 通用"大模型 + 机器人"方案 | 语言到动作/目标点的直连 | 技能组合的声明式编排、能力契约、板级交付与仿真/真机标识分离 |

### 2.3 现有技术的具体缺陷

| 编号 | 缺陷 | 现场可观察后果 |
|---|---|---|
| D1 | 应用代码绑定特定板卡 + OS + 中间件：没有"技能"这一层可移植合约 | 换板/换 OS/换机型必须改业务代码；同一作业在每个目标上各写一遍 |
| D2 | 技能没有统一合约（输入/输出 schema、能力依赖、前置条件、超时、取消、恢复、安全等级、版本） | 应用直调 topic/接口；失败原因不可归类；无法做契约测试与回归 |
| D3 | 板级"未知"被当作可用：未实测的 OS/内核/Python 标签/平台标签按默认值放行 | 开发机上"通过"，到目标板装不上或起不来，且无人预警 |
| D4 | 跨架构交付不可复现、不可审计：目标端联网装依赖、依赖闭包缺失、产物不可复算、卸载误删 | 隔离网无法交付；同一版本两次构建结果不同；回滚/卸载有数据风险 |
| D5 | 能力声明与实现漂移：声明了做不到的能力（虚假声明），或实现多于声明以致策略层静默拒绝 | 策略通过但无人实现（悬空能力），或任务被"莫名其妙"拒绝而无人知道原因 |
| D6 | 仿真与真机能力不分、配置中的"未验证"值可用于生产 | 仿真结论被当作真机能力；上线失效 |
| D7 | 同一技能的多实现（传统算法/学习策略/VLA/仿真）共存时无确定性路由 | 同一请求在两台机器上走不同实现，结果不可比、不可复现 |
| D8 | 运行期绑定散落硬编码（机型分支、手写后端配置），随契约演进静默过期 | 配置字段缺失导致装配失败，或功能"悄悄"不可用（实测已发生两次） |
| D9 | 多虚拟机分域构型（Hyper）的 VM 数量、编号、IP、OS 与角色映射被硬编码进业务代码 | 构型换代即改代码；2VM 构型合并部署时安全边界被一并合并 |

**要解决的技术问题**：如何让"面向特定板卡与特定 OS 的机器人开发"从**逐板逐机型的手工工程**，变成一条**声明驱动、能力契约约束、跨架构可复现、失败即拒绝**的标准化路径，同时保证技能组合的语义在仿真与边缘目标上一致。

## 三、发明内容

### 3.1 发明目的

1. 提供**技能包**这一可移植单元，使应用只组合技能、不接触板卡/OS/中间件/机型；
2. 提供**声明式技能组合编排**，在编译期完成引用可达性、类型与未定义状态检查；
3. 提供**分级声明体系**（本体 / 板级 / 构型 / 运行期绑定），板级与构型事实来自签名发布元数据而非代码；
4. 提供**装配期能力契约单向校验**，消灭"悬空能力"与"虚假声明"；
5. 提供**跨架构可复现交付链**：开发端按声明生成产物与离线依赖库，目标端**零联网**安装、**失败关闭**；
6. 保证同一技能组合在仿真与板级目标上**语义一致**，且仿真标识与未验证配置不可越界。

### 3.2 技术方案总述（四层 + 一条交付链）

```text
第 1 层  技能包（Skill Package）——可移植的作业单元
   skill.yaml: 输入/输出 schema、能力依赖 requires、前置条件、超时、
               取消策略、恢复策略、安全等级、版本、提供者选择条件
   *.input.json / *.output.json: 参数与结果契约（含错误码）
                 ↑ 不含板卡 / OS / 中间件端点 / 机型信息

第 2 层  技能组合编排（Composition）——声明式状态机
   guard / skill / retry / safe_hold / handover / terminal
   编译期：上下文引用类型、可达性、未定义状态检查 ⇒ 确定性执行计划
   循环只能经显式 retry（须有最大次数、退避、总时限）；不支持任意脚本

第 3 层  分级声明（Declarations）
   RobotProfile   : 能力集合、关节/传感器、工作空间与策略边界
   BoardProfile   : OS、架构、kernel、python_tag、platform_tag、glibc_min、
                    OCI/ROS2/systemd、适配器、内存/磁盘、镜像摘要、验证状态
   HyperProfile   : VM 数量、各 VM 的 OS 角色与承载服务角色（引用签名发布元数据）
   MachineBinding : 机型 → Profile + 后端入口 + **后端配置来源** + 安全策略
   规则：任何未实测字段必须写 unverified；unverified ≠ 可用

第 4 层  能力提供者（Provider）与前缀隔离
   classical / learned / VLA / teleop / replay / sim
   按 (能力, 运行模式, 健康, 资源, 优先级, 名称) 确定性选择

交付链（开发端 x86_64 → 目标端 aarch64）
   读声明 → 生成 SDK wheel + 运行时包 + 板级包 + 离线依赖库 + 清单/校验和/SBOM
        → 传输（ssh 或介质）→ 目标端预检 → 失败关闭式安装 → 声明一致性自检
        → 服务启动 → 健康检查 → 证据落盘
```

### 3.3 八项核心机制（对应权利要求）

- **M1 技能包合约**：每个技能包声明输入/输出 schema、能力依赖、前置条件、超时、取消/恢复策略、安全等级与版本；提供者以"类型 + 选择条件"声明，**不含**板卡/OS/中间件端点；技能包自带最小示例与成功/失败路径契约测试。
- **M2 组合编排的编译期确定性**：受限节点类型集合；循环只能经显式重试节点声明且必须有最大次数 + 退避 + 总时限；编译期做类型/可达性/未定义状态检查；**不支持任意脚本**（消除不可静态分析的行为）。
- **M3 分级声明与"未知即不可用"**：本体/板级/构型/运行期绑定四类声明；构型的 VM 数量、编号、IP、OS 与角色映射**引用**签名发布元数据，不在代码中硬编码；未实测字段一律 `unverified`，且在预检中**视为失败**（本实施：`profile_check.py --board` 对未实测声明**退出码 2**）。
- **M4 能力契约单向校验**：装配期强制"本体声明 ⊆ 实现"，声明了未登记或未实现的能力 ⇒ 装配失败；实现多于声明 ⇒ 只记入装配报告（`undeclared_motion_capabilities`）供审计，**不拦装配、也不使该能力对外可用**。该单向性允许同一提供者类服务多台能力子集不同的机器人。
- **M5 运行期绑定声明化**：机型 → Profile + 后端入口 + **后端配置来源** + 安全策略全部来自声明文件；后端配置**由场景/模型报告生成**（禁止手写），从机制上消除"配置随契约演进静默过期"。
- **M6 跨架构可复现交付**：开发端读产物矩阵声明（唯一事实来源）生成三类产物 + 离线依赖仓库；依赖清单必须为**传递闭包**且由工具解析后**经人工确认回填声明**（脚本不得自动改写声明）；两次构建的产物 SHA-256 逐位相同作为可复现判据。
- **M7 目标端预检与失败关闭安装**：逐项比对架构/OS/解释器标签/平台标签/内存磁盘/服务管理器/依赖冲突；`unverified`、缺失或不符 ⇒ 拒绝安装（非零退出码）；安装后运行声明一致性自检，**自检失败不启动服务**；卸载仅依据安装记录中登记的文件（清单外文件即拒绝卸载）。
- **M8 仿真—板级语义一致与标识分离**：同一技能包集合与公开接口语义在仿真与板级目标执行；`simulation` 标识随执行结果回传；标记为仿真专用的安全策略不得用于非仿真目标；未验证配置仅允许在仿真目标执行。

### 3.4 有益效果（含实测）

| 效果 | 机理 | 证据（精确数字，来源见 §11） |
|---|---|---|
| **接入一台全新命名的机器人与新作业，不需要写机型代码** | 技能包 + 声明层 + 通用构建器；机型差异只在声明 | 第三台机型干跑（合成 4 自由度臂 + 平行双指夹爪，关节/零件命名与既有两台**刻意完全不同**）：`profile_check.py` **零代码 PASSED**；`build_baseline.py` 推进到运动学求解并按门禁**显式失败**（`ValueError: 夹持区中心与抓取目标不一致: \|measured - target\|=0.008441 m`）；由该干跑暴露并修掉的两处写死假设，对既有 UR5e 的参考姿态**逐位不变**（0 处差异 > 1e-9，姿态偏差仍为 `0.006467°`） |
| **能力声明诚实且不可悬空** | 单向能力契约 + 策略层能力门禁 | UR5e 未接视觉时：装配报告 `declared=[move_joint, pick_object, stop]`、`undeclared_motion_capabilities=["visual_pick"]`、`passed=true`；提交 `visual_pick` ⇒ `FAILED / IRAF-SKILL-PROVIDER-UNAVAILABLE`，原因 `RobotProfile 缺少能力: ['visual_pick']`（在策略层拒绝，**不是**落到后端才失败） |
| **板级未实测字段不会被当作可用** | 未验证即拒绝（非零退出） | `profile_check.py --board profiles/boards/e300.yaml` ⇒ 退出码 **2**；加 `--allow-unverified` 时摘要写 `verified: false`，可审计 |
| **跨架构交付可复现、可审计** | 集中声明 + 离线依赖 + 双次构建对账 | SDK 产物连续两次构建 SHA-256 **逐位相同**；依赖闭包缺失会导致离线安装失败，故矩阵明列传递闭包（实测：`mujoco→absl-py/etils[epath]/glfw/numpy/pyopengl`，`etils[epath]→fsspec/zipp`） |
| **错标签依赖无法混入交付物** | 平台标签门禁（白名单 + 黑名单双判） | 抓取脚本拒绝 `win_arm64` / `win32` / `win_amd64` / `macosx`（实测 numpy 索引混入 `win_arm64` 干扰项）；目录与登记清单不一致 ⇒ 退出码 **4** |
| **技能组合语义可跨机型/跨环境复用** | 技能包不含机型与板级信息 | Piper（6 轴臂 + 平行夹爪，眼在手）与 UR5e+2F-85、以及四足 Go2 共用同一套技能合约与运行时；差异只在 `profiles/` 与 `config/` |
| **同一技能的多种实现在同一板上确定性路由** | Provider 选择条件 + 优先级 + 名称排序 | `skills/locomote/skill.yaml` 等以 `selector: {mode: simulation}` + `priority` 声明；无候选返回 `IRAF-SKILL-PROVIDER-UNAVAILABLE`，不静默换实现 |
| **配置漂移从机制上被消除** | 后端配置由场景报告生成 | 实测两次真实过期事故：夹爪几何字段改为必填后旧手写 JSON 缺 `wrist_body`/`*_finger_geom` ⇒ 装配期直接失败；视觉入口声明式化后旧 JSON 缺 `vision` 段 ⇒ `visual_pick` 报"未提供视觉证据路径"。改为 `scripts/emit_backend_config.py` 生成后不再复现 |
| **执行时安全边界不可旁路**（与附件 A 联动） | 唯一路径 `TaskFlow → SkillRuntime → PolicyGateway → Provider` | 见附件 A；本文以从属权利要求形式收编 |

**因果分离**：上表"零代码 PASSED"的原因是**声明驱动 + 通用构建器**，不是因为放宽了判据；同一干跑在声明不自洽时**确实被门禁拒绝**（`|measured - target| = 0.008441 m`），说明门禁在起作用的同一路径上也确实在拒绝。

## 四、权利要求书草案

### 权利要求 1（独立权利要求，方法）

一种机器人技能组合开发及跨板级部署方法，其特征在于，包括：

**S1** 提供技能包集合，每个技能包至少声明：技能名称与版本、输入数据结构、输出数据结构、所需机器人能力集合、前置条件、超时、取消策略、恢复策略、安全等级，以及一个或多个能力提供者的类型与选择条件；所述技能包与具体板卡、操作系统、消息中间件端点及设备节点无关，具体端点与命名空间由下述声明提供；

**S2** 接收以声明式组合描述编排的技能组合，所述组合描述由受限节点类型构成，所述受限节点类型至少包括守卫节点、技能节点、重试节点、安全保持节点、人工接管节点与终态节点；其中循环仅通过显式重试节点声明，且所述重试节点必须声明最大尝试次数、退避与总时限；将所述组合描述编译为确定性执行计划，并在编译期对上下文引用的类型、可达性与未定义状态进行检查；所述组合描述不支持任意脚本执行；

**S3** 提供分级声明，所述分级声明至少包括：本体配置声明，用于声明能力集合、关节与传感器、工作空间与策略边界；板级配置声明，用于声明操作系统、架构、内核、目标解释器标签、平台标签、最小运行时库版本、容器运行时、消息中间件、加速器、内存与磁盘、镜像摘要及验证状态；构型配置声明，用于声明虚拟机数量、各虚拟机的操作系统角色与其承载的服务角色，且所述虚拟机数量、编号、地址、操作系统与角色映射**引用**已签名的发布元数据而不在程序代码中硬编码；其中任何未经实测的字段必须被写为未验证值；

**S4** 在装配期执行能力契约校验：当所述本体配置声明的能力集合中存在未被所述能力提供者实现的能力项时，装配失败；当所述能力提供者实现了所述本体配置未声明的能力时，仅将该能力项记入装配报告供审计，不导致装配失败且不使该能力对外可用；当所述本体配置声明了未登记的能力项时，装配失败；

**S5** 由声明解析运行期绑定：机型标识映射至本体配置、后端入口、后端配置来源与安全策略；所述后端配置由场景报告或模型报告生成，业务代码中不出现机型条件分支，且不以人工书写的配置作为所述后端配置来源；

**S6** 在开发端依据所述板级配置声明所声明的目标架构、目标解释器标签与目标平台标签，生成交付物集合，所述交付物集合至少包括：与架构无关的软件开发包、运行时包、板级包、离线依赖仓库、文件摘要清单与软件物料清单；所述离线依赖仓库所依据的依赖清单为传递闭包，且该清单由工具解析后经人工确认回填至声明文件，而不由脚本自动改写声明文件；

**S7** 在目标端执行预检与失败关闭式安装：逐项比对声明的架构、操作系统、解释器标签、平台标签、内存与磁盘、服务管理器以及已安装依赖冲突；当任一声明字段为未验证值、缺失或与实测不符时，拒绝安装并以非零退出码结束；安装完成后执行声明一致性自检，自检失败则不启动服务；

**S8** 使所述技能组合在仿真目标与所述板级目标上使用同一技能包集合与同一公开接口语义执行；将仿真标识随执行结果回传；标记为仿真专用的安全策略不得用于非仿真目标；未验证的配置仅允许在仿真目标上执行。

### 权利要求 2（从属：技能包契约测试）

根据权利要求 1 所述的方法，其特征在于，每个技能包附带成功路径与失败路径的契约测试，且将错误码映射为可操作的中文诊断信息；技能包声明的输入结构、输出结构与实现返回的字段一致性由契约测试锁定。

### 权利要求 3（从属：平台无关能力词表门禁）

根据权利要求 1 所述的方法，其特征在于，所述能力集合使用与平台无关的规范词表，并以可执行的校验门禁禁止厂家专有语义（厂家关节名、通信域标识、校验细节等）出现在通用技能合约层与公共接口层。

### 权利要求 4（从属：确定性提供者选择）

根据权利要求 1 所述的方法，其特征在于，当同一技能存在多个能力提供者时，依次按所需能力、运行模式、选择条件、健康状态、资源限制与优先级进行过滤，并在候选并列时按优先级与提供者名称确定性排序；无候选时返回"提供者不可用"错误，而不静默改用其他实现。

### 权利要求 5（从属：构型不匹配的硬拒绝）

根据权利要求 1 所述的方法，其特征在于，启动时比对所述构型配置声明与制品中的板卡标识、虚拟机拓扑、虚拟机类型、管理程序与内核版本、以及构型版本文件；任何不匹配均禁止进入边缘生产档，且**不自动回退**到另一构型。

### 权利要求 6（从属：合并部署不合并安全边界）

根据权利要求 1 所述的方法，其特征在于，当所述构型配置声明为两个虚拟机、且运动控制角色与设备主站角色部署于同一虚拟机时，所述两个角色仍以不同进程、不同用户与能力集、不同资源限额以及设备独占策略部署，其安全边界不被合并。

### 权利要求 7（从属：安装可回滚且卸载不误删）

根据权利要求 1 所述的方法，其特征在于，安装到按版本命名的目录并以激活链接切换版本，失败时回滚到上一版本；卸载仅依据安装记录中登记的文件清单执行，检测到清单外文件即拒绝卸载。

### 权利要求 8（从属：唯一执行路径与安全链）

根据权利要求 1 所述的方法，其特征在于，所述技能组合的执行必须经"任务编排 → 技能运行时 → 策略网关 → 能力提供者"的唯一路径：身份取自受信传输层而非请求体；由服务端生成执行标识并在（主体、租户、操作）域内绑定幂等键与请求摘要；下发控制量之前获取含单调围栏令牌的资源租约并校验执行活动态、令牌与能力一致性；执行终态一经写入不可被回调改写，失败后的恢复以上层新建执行并保留因果关联的方式完成；安全事件后将相关资源隔离，且仅在安全事件标识一致、控制器回送安全状态确认、经认证操作者具复位权限三项同时满足时解除隔离。

### 权利要求 9（从属：控制解新鲜度门禁与双停止语义）

根据权利要求 8 所述的方法，其特征在于，对由求解器周期性生成的控制解，在消费侧判定其解龄：当解龄超过声明的控制周期倍数、或解龄不可信、或求解状态分类不属于可用集合时，停止使用该控制解且不输出任何控制解；并且按状态选择停止语义：移动状态下选择"减速到零并保持位形"的阻尼保持，急停或安全事件下选择力矩释放；当阻尼保持在声明的停止时限内未满足末速、倾角与机身高度判据时，输出显式失败与最后的测量状态。

### 权利要求 10（从属：声明式随机化泛化验证）

根据权利要求 1 所述的方法，其特征在于，对新机型或新板级目标执行声明式随机化验证：在声明的工作空间内按面积均匀方式采样目标位姿，每一轮使用以基础种子派生的独立子种子，报告同时记录基础种子与每轮子种子；采样阶段不做可达性预筛，退化位形记为合法采样并由下游门禁拒绝且归类为预定义的拒绝原因。

### 权利要求 11（独立权利要求，系统）

一种机器人技能组合开发及跨板级部署系统，其特征在于，包括：

## 六、具体实施方式

### 实施例 1：一台全新机器人的零代码接入（对应 S1/S3/S4/S5）

**资产**：合成的 4 自由度平面臂 + 平行双指滑轨夹爪；关节命名 `q1..q4`，指腹 `pad_l/pad_r`，指节 `pinch_l/pinch_r`，法兰 `flange` —— 与既有两台机型（Piper、UR5e）**刻意完全不同的命名**，以确保"因名字恰好相同而跑通"的隐藏耦合会暴露。

**步骤与实测结果**：

| 步骤 | 输入 | 结果 |
|---|---|---|
| 1. 声明校验 | 新增 profile + 基线配置（**零 Python 代码**） | `scripts/profile_check.py` **PASSED** |
| 2. 通用构建器 | 同上 | 推进到运动学求解阶段后按门禁**显式失败**：`ValueError: 夹持区中心与抓取目标不一致: \|measured - target\|=0.008441 m` |
| 3. 定位到真实耦合 | — | 求解器原先把"法兰 x 轴"写死为夹爪开合轴；该机型开合轴为法兰 y 轴 ⇒ 姿态约束永不满足（姿态偏差 `20.648°`、开合轴偏差 `86.536°`） |
| 4. 修法 | 从模型**实测局部轴**构造目标旋转（不新增约定） | `R_target = W · Lᵀ`，自证 `R·Rᵀ = I`；实测局部轴不垂直即显式失败 |
| 5. 回归验证 | 既有 UR5e | 参考姿态**逐位不变**：0 处差异 > 1e-9，姿态偏差仍为 `0.006467°` |

**诚实缺口**：该第三机型尚未跑到抓取验收（需把目标放到实测可达集内）；"声明正确 ≠ 能抓住"依然成立。

### 实施例 2：跨板级/跨 OS 交付链（对应 S6/S7）

**开发端**（x86_64）：`bash deploy/sdk/build_sdk.sh` → 产物三类 + `manifest.json` + SBOM + SHA-256 清单；`bash deploy/sdk/fetch_wheelhouse.sh` → 按声明的 `python_tag`/`platform_tag` 抓取离线依赖（标准库直读 PEP 503 索引，按标签门禁下载）。

**目标端**（aarch64）：`install.sh` 预检 → 离线安装 → 写环境 → `profile-check` → 启动服务 → 健康检查；`verify.sh` 输出证据 JSON；`uninstall.sh` 仅按安装记录卸载。

**退出码契约（全脚本统一）**：0 成功；1 参数/用法错误；2 预检失败（架构/Python/依赖/声明缺失或 `unverified`）；3 安装或构建失败；4 校验失败（摘要、清单、IDL 不兼容）；5 健康检查或 `profile-check` 失败（已安装但拒绝启动）。

**已实测（开发端）**：产物可复算（两次构建 SHA-256 逐位相同）；错标签依赖被拒（`win_arm64` 等）；目录与登记清单不一致 ⇒ 退出码 4；`unverified` 板级声明 ⇒ 退出码 2。
**DEFERRED（目标端，板卡不在场）**：真实安装、`/health`、AgentOS 联通、断电重启幂等恢复 —— **不得**以 dry-run/mock 结果代替。

### 实施例 3：同一技能组合跨三台本体（对应 S1/S8）

| 本体 | 作业 | 差异所在 | 核心/技能层是否改动 |
|---|---|---|---|
| AgileX Piper | 视觉抓取放置 | `profiles/piper_mujoco.yaml` + `config/machines/piper.yaml` | 否 |
| UR5e + 2F-85 | 抓取（无视觉） | `profiles/ur5_mujoco.yaml` + 装配脚本 | 否 |
| Go2 EDU | 站立/停止/移动 | `profiles/unitree_go2_mujoco.yaml` + `config/go2_loopback.yaml` | 否（能力未实现时显式拒绝） |

**实测数字（Piper）**：接触力 `0.240676 / 0.244112 N`、抬升 `0.087184 m`、位姿偏差 `0.002826042685491991 m`（容差 0.005）；随机化 25 次采样位置误差均值 `0.963 mm`、标准差 `0.419 mm`、最大 `1.773 mm`，姿态误差均值 `0.880°`、最大 `1.480°`。

### 实施例 4：边缘板级目标（四足）的执行与安全降级（对应 S8 + 权利要求 9）

### 实施例 5：【设计稿】Hypervisor 多虚拟机分域构型

三个正式构型：`MQ50-E300-3VM-LPR`（VM0 Linux / VM1 Linux RT / VM2 RTOS）、`MQ50-E300-3VM-LPP`（VM0 Linux / VM1 Linux RT / VM2 Linux RT）、`FIREFLY-RK3588-2VM-LR`（VM0 Linux / VM1 Linux RT）。角色映射：VM0 = AgentOS + 控制/数据面；VM1 = 运控面（ROS 2）；VM2 = 主站适配与安全看门狗。三构型共享同一技能合约与声明语义，但各自独立产出 bundle、SBOM 与验收报告。2VM 构型中运控与主站同 VM 时，仍以不同进程、用户/能力集、资源限额与设备独占部署（权利要求 6）。S600 无正式发布构型 ⇒ 保持 `unverified`，不进发布矩阵。**实现状态：设计基线已定稿，未实现。**

## 八、替代实施方式与规避设计空间

1. **技能包载体**：可用 YAML/JSON/Protobuf/数据库记录承载；权利要求应以"声明"与"字段语义"限定，不绑定文件格式。
2. **组合编排语言**：可用状态机、行为树、任务图或工作流 DSL 实现；权利要求已用"受限节点类型 + 循环仅经显式重试"限定（这是可专利的实质约束），可覆盖行为树等替代实现。
3. **板级声明粒度**：可拆为多文件或合并为单文件；`python_tag`/`platform_tag` 可替换为等效的 ABI/运行时标识（权利要求写"目标解释器标签与平台标签"）。
4. **交付形态**：L1 纯 Python + 离线 wheelhouse（本实施）、L2 多架构 OCI 镜像、L3 板级原生包（RPM/deb/BSP）——权利要求限定"交付物集合"而非具体形态，覆盖三者。
5. **预检实现**：可在安装脚本、独立校验工具、服务启动前置钩子或 CI 中执行；权利要求限定"安装前 + 自检后启动"的时序，覆盖各实现位置。
6. **能力契约校验位置**：可在装配期、服务启动期或 CI 期执行；权利要求限定"装配期"并允许等效的启动前校验。
7. **反向规避风险**：竞争者可能把板级声明"内联进代码常量"以规避 S3/S7。故权利要求 1 必须同时保留 S3（未实测字段须写未验证值）与 S7（未验证值即拒绝安装）——**"声明未实测 + 拒绝放行"这一对特征是规避不掉的内核**；再叠加 S4（能力契约单向）与 S6（离线依赖闭包 + 双次构建对账）形成组合壁垒。

## 十三、诚实边界与不主张事项

1. **仿真与开发端为主**：全部实测数据来自 MuJoCo 仿真或 x86_64 开发端脚本；目标 aarch64 板级的真实安装、`/health`、AgentOS 联通为 **DEFERRED**（板卡不在场），不得表述为已具备板级能力。
2. **【设计稿】标注**：Hypervisor 多 VM 分域构型的实现（实施例 5）、`TaskDelegation` 委托、多本体交接互锁（P8）、P4 的一部分均未实现，正文已逐条标注。
3. **"零代码接入"的边界**：实施例 1 只证明"能被声明识别并推进到运动学求解 + 门禁正确拒绝"；**不**证明该机型能完成抓取验收（目标位姿需在实测可达集内，且抓取还依赖夹爪几何、摩擦与力阈值的物理合理性）。
4. **未做专利检索**：见 §9.3 末的诚实声明。
5. **数字的环境绑定**：本机为 x86_64（4 核 i5-6400，`powersave` 调频，存在并发负载）；性能类数字（如 MPC 整步墙钟 P50 `7.8386 / 8.5328 ms`）引用时须连同环境说明，且最终证据应来自目标架构。
6. **不主张**：本发明不主张任何具体中间件（ROS 2/DDS）、任何具体规划或控制算法、任何具体机器人本体与厂家 SDK、任何具体包管理或容器机制本身。
