## 0. 发明锚点（先对齐，否则写出来必被推翻）

使用者本轮给出的产品口径（原话要点）：

> "x86 完整运行机器人应用框架"；"x86 运行仿真 Provider，边缘侧**智控域和运控域运行另外的**
> 机器人应用框架"；"机器人应用框架基于 **TaskFlow / Skill Manager** 以及 **MCP 注册到 AgentOS** 的方式"；
> "机器人应用框架**可以有自己的 agent API 对接外部 LLM**"。

翻成一句话的"卖什么"：
**同一套机器人应用框架，能在四种落点（x86 全栈 / 板卡智控域 / 板卡运控域 / 跨机仿真执行面）上
以同一份技能与判据一致运行，并同时具备两种对外接口（平台侧 MCP 任务级入口、框架自带受约束意图通道）。**

三个候选锚点：

| 候选 | 主发明表述 | 证据强度 | 风险 |
|---|---|---|---|
| A（推荐） | **控制面/执行面跨机分离**：任务与判据留在边缘运行面，执行能力以独立进程 + 版本化接口跨机替换为仿真 Provider，且两端语义一致 | 最硬：跨机实测 + 租约三路径 + 复位→动作数字 | 需与 P1（声明交付链）划清界限 |
| B | **单一声明驱动的多落点一致运行**：一份技能包与判据，靠声明区分四落点（含同机双域路径隔离） | 中：真装只覆盖 x86 sim-x86 与 E300 cohost；motion-split 未跑 | 与 P1 的 S3/S6/S7 高度重叠，易被认定为同一发明 |
| C | **外部智能体接入机器人框架的语义收口**：只暴露任务级接口 + 路由表 + 显式过滤码 + 自带意图通道 | 硬：板上 MCP 实测 + 意图层正负路径 | 与"平台侧"耦合，需把权利要求锁在框架侧 |

**推荐锚点 A 为主发明**，理由：它同时命中使用者两条口径（x86 跑仿真 Provider、边缘跑框架），
且是本轮唯一有"同一动作链在两种执行面之间替换、并留下逐条数字"的方向；B 的独有部分收成从属，
C 单列同日申请（技术问题独立）。若目标是"一件申请覆盖全部四条口径"，则改为锚点 B，代价是独权更抽象、
审查时更容易被 P1 命中——**这两条路必须由使用者拍板，不自行决定**。

## 2. P9（主申候选）跨机仿真能力提供方

### 2.1 技术问题（换掉这段机制，功能是否还成立？不成立 ⇒ 是发明点）

机器人技能栈要做"开发即验证"，但真实执行器与控制器不在开发机上；把仿真引擎装到边缘板卡上会撞三件事：
① 认证基线（板卡侧 OS/ABI 与图形/物理依赖）与仿真依赖冲突；② 板卡资源与实时域隔离不允许；
③ 若开发机上另写一套"仿真版框架"，判据就与真机链路不同源，验证结论无法互相印证。
再往前一步：跨机后执行面变成**有延迟、会失败、可能僵尸**的远程进程，控制面必须仍能保证
"同一执行器任一时刻只有一个控制源、旧令牌不生效、终态不可复活"——这些在单机内是进程内互斥，
跨机后必须变成**带租约与单调围栏令牌的跨进程协议**。

### 2.2 机制（可执行特征，按独权顺序）

- S1 控制面（任务编排 / 技能执行 / 策略放行）与执行面（能力实现）**分属不同进程、不同主机**；
  二者之间**只**经版本化接口通信，且接口带 deadline、取消、健康检查、最小权限凭据。
- S2 执行面以**能力自报**方式暴露清单：健康查询返回 `ready`、`simulation` 标志、能力名集合、
  运行清单（模式、急停状态）；控制面在**装配期**用"声明 ⊆ 实现"单向核对，实现多于声明只记不拒。
- S3 每次物理动作由**服务端**生成执行标识与幂等键；客户端不得自造标识（跨机后这是"谁负责记账"的分界）。
- S4 执行域租约：租约为**单次动作**粒度，在成功 / 拒绝 / 失败**三条路径**均释放；
  释放后下一次动作必须取得**单调递增**的新围栏令牌；旧令牌或终态执行再下发的控制请求被拒。
- S5 同一份任务编排、场景与判据在两侧复用，只替换执行面实现与配置声明；仿真结论**随结果回传**
  仿真标志，仿真专用安全策略不得用于非仿真执行面。
- S6 故障语义：执行面不可达 / 未就绪 / 拒绝 / 超时，一律显式失败并给出可诊断码，
  不允许控制面"重试到成功"或把上次结果当本次结果。

### 2.3 技术效果（逐字数字 + 出处，禁止四舍五入）

- 跨机能力自报：`reachable=true ready=True simulation=True`，
  `capabilities=6 move_joint,pick_object,place_object,reset_scene,stop,visual_pick`，
  `inventory: mode=simulation safety={'estop': False}`
  （`docs/debug/2026-10-26-x86-sdk-provider-service.md` §4）。
- 复位→立刻动的执行域释放效果：`[1] reset_scene accepted 0.08s`、`[2] move_joint accepted 0.01s`、
  `[3] move_joint accepted 0.01s`，总墙钟 `0.10s`，三次 `execution` 互不相同，**无 `IRAF-RESOURCE-BUSY`**（同上 §4）。
- 修复前对照（同一探针）：`[2] pick_object accepted=False code=IRAF-RESOURCE-BUSY token=0`，
  残留租约 `120.0` s；修复后 `accepted=True token=2`、残留租约 `[]`，回归 `27 passed`
  （`docs/debug/2026-10-26-provider-lease-not-released-on-success.md` §1/§4）。
- 跨机 MCP 走同一执行面的端到端：`SUCCEEDED` / `1f2e486c-96d1-552b-afec-ac6d7e3f2332`，
  读回同一条（`docs/mcp-binding.md` §4）。

### 2.4 证据索引

`src/iraf_adapters/remote/provider_service.py`（ExecutionRegistry / Invoke 三路径释放 / Health 自报）、
`src/iraf_core/authority.py`、`src/iraf_core/runtime.py:160-172`（板卡侧执行域租约）、
`docs/deploy-topology-and-domain-split.md` §1/§2、`docs/debug/2026-10-16-remote-provider-cross-machine.md`、
`docs/debug/2026-10-26-*.md` 两篇、`tests/unit/test_provider_lease_release.py`（5 例）。

### 2.5 权项要点（功能限定，禁写实现名）

独权写 S1~S6 的时序与否定式限定：**"在下发任何控制量之前"校验活动态/令牌/能力**；
**"释放后必须换发更大令牌"**；**"成功返回即释放执行域租约"**（这是与"按连接持有"的关键区别，也是
最容易被规避设计绕过的点，必须进独权）。从属可加：能力自报 + 装配期单向核对；仿真标志随结果回传；
同机双执行面时进程/权限/资源限额/设备所有权四项分离。

### 2.6 规避空间（代理机构最需要的一节）

1. 不释放租约、靠 TTL 过期 ⇒ 仍落入"动作前必须取得新令牌"的从属；但若能证明"从上位任务持有"，
   可能绕开独权 ⇒ 独权里补"租约粒度与执行请求粒度一致"。
2. 由客户端生成执行标识 ⇒ 落不进 S3；故 S3 必须单独成项而非只写在说明书。
3. 用 HTTP/REST 而非版本化二进制接口 ⇒ 不受 S1 字面限制，但"deadline/取消/健康检查"组合可覆盖。
4. 仿真与真机各写一套判据 ⇒ 直接落到 S5 的反面，作为对比实施例写清楚（判据漂移的后果要写数字）。

## 3. P10 装完 SDK 即有 Provider（声明驱动的服务固化）

### 3.1 技术问题

执行面只能由开发者在会话前台手工拉起 ⇒ 会话断/机器重启即丢，违反"交付即可用"；
而把服务写进安装脚本又会与"交付包不含脚本目录"冲突（单元指向仓库脚本 ⇒ 目标端找不到入口）；
场景资源用相对路径引用网格文件，拷进版本目录即断链；凭据文件只进回滚清单、不进安装记录 ⇒ 卸载残留。

### 3.2 机制

- S1 把"服务单元、端口、装配单、场景、凭据"全部升为**安装角色的声明**（同一份声明决定装什么、起什么、
  卸载核验什么），校验器对"仿真执行面角色"强制要求三件齐备：服务声明 + 装配单模板 + 场景声明。
- S2 服务入口下沉为**包内可执行模块**，仓库脚本只做薄壳 ⇒ 安装物自包含，单元不依赖源码目录。
- S3 单元落点由**作用域**推导（系统作用域 / 用户作用域不同落点），并在非系统作用域**强制剔除**
  身份切换与网络目标依赖（否则目标端起不来，见 3.3 的两个真实失败）。
- S4 场景引用的资源目录随包安装，引用改写为**包内相对路径**（安装物自包含，与 S2 同一条主线）。
- S5 凭据写 600 文件并**登记进安装记录**，卸载按记录删除（残留核验可机器判）。
- S6 结构性校验规则把上述要求做成"缺一即拒装"，并区分"协议常量地址"与"具体机器地址"
  （后者不得进模板）。

### 3.3 技术效果（含两个真实失败，作为"为什么必须 S3"的因果证据）

```
安装：退出码 0；lib 依赖 + 桩 11 个；IRAF_BACKEND_CONFIG 由场景报告生成 3759 字节；记录 9043 个文件
服务：systemctl --user enable --now iraf-provider → active，LISTEN *:50052
窗口：0x620000b "MuJoCo : piper_description" 1280x720
卸载：删除 9050 项；verify_residue 六路 files/dirs/env_files/ports/processes/unlisted 全 0，unit exists=False
校验器：105 项检查，0 项未通过
```
失败对照（同文件 §4.1）：`Unit network.target not found`（起不来）；
`status=216/GROUP Failed to determine supplementary groups`（用户作用域写了 `User=`）；
`Error opening file '../../../piper_ros/.../link1.STL'`（相对 mesh 断链）。
出处：`docs/debug/2026-10-26-x86-sdk-provider-service.md` §4/§4.1。

### 3.4 权项要点与边界

主张"由声明推导服务固化 + 安装物自包含 + 凭据进安装记录 + 结构性规则拒绝"，**不主张** systemd 机制本身、
不主张具体路径/端口/用户（写进不主张清单）。与 P1 的关系：P1 主张的是"声明 → 装得上/卸干净"的整体链，
P10 是其"执行面服务化"的具体化 ⇒ **建议作 P1 分案或同日申请**，避免被自己命中。

## 4. P11 北向语义收口（MCP 注册到平台）

### 4.1 技术问题

平台侧（AgentOS 类"通用智能体平台"）自己有 skills / tools / 工作流。若把机器人技能逐个注册成平台工具：
① 平台可绕过技能管理器直接执行技能，契约校验、策略判定、证据链全部被跳过；
② 一句话有歧义（"抓取/放置"既可能是平台动作也可能是机器人任务），平台模型易错选；
③ 实测平台**0 次**调用机器人框架工具，反而用宿主命令读源码、自己跑脚本、甚至改了平台侧旁路技能
   来"用 shell 拉起我们的服务"——不是不会用，而是被旁路指挥着绕开主路。

### 4.2 机制（全部在框架自身，不改平台）

- S1 北向**只暴露任务级接口**（提交任务 / 查询执行事实 / 进入-退出工作模式），并在构建期用静态检查
  **禁止**出现技能级工具名 ⇒ "平台不得绕过技能管理器"从约定变成机器可查的门禁。
- S2 进入模式时一次性下发**路由表**（技能清单 + 每技能意图示例 + 分派守则 + 成功/被过滤两个示例）
  与固定顺序的下一步说明，使外部模型"照着用"而不是自行设计执行路径。
- S3 语义判定权留在框架：无法判定为机器人任务时，返回**独立的过滤码**（与"解析失败"分属不同异常与
  错误码），外层据此回退到自己的处理；过滤不得被表述为失败，也不产生任何机器人动作。
- S4 模式标记是**语义收口而非安全边界**：不放大权限、不跳过策略网关，安全上限仍只来自签名配置。
- S5 反旁路约束写进接口描述、返回值与资源示例（"唯一受支持入口"），且不修改平台容器/包目录。
- S6 传输双形态：同机子进程（标准输入输出）与跨机流式 HTTP（允许 Host 白名单 + 缺凭据即失败关闭）。

### 4.3 技术效果

- 板上实测（0.3.5，跨机 HTTP）：`TOOLS ['iraf_robot_mode','iraf_submit_task','iraf_get_task']`；
  `status` → `mode=idle | skills=13 | simulation=True`；`enter` → `mode=robot_dev, remaining_s=599`；
  `submit` → `SUCCEEDED | skill=pick_object | robot_mode=robot_dev | execution_id=c73aadf7-fb53-5e35-8afa-a9d529d623a4`；
  `exit` → `mode=idle`（`docs/mcp-binding.md` §2）。
- 0.3.9 复核：`TOOLS` 5 个、`RESOURCES` 3 个；`mode=robot_dev | skills=13 | intents=13 |
  examples=['robot_task','non_robot']`；过滤用例返回 `IRAF-NOT-ROBOT-TASK` 且下一步明示"由平台自己处理、
  不要重试"（同文件 §9.1）。
- 旁路被消除的对照：改前平台 0 次调用框架工具、读取十余个源文件（同文件 §9）；改后进入模式只做只读盘点、
  零 `execution_id`（`docs/mcp-binding.md` §8.5）。

### 4.4 权项要点与边界

独权要写"任务级接口集合的**静态门禁**"、"过滤码与解析失败分离"、"模式只读盘点且不放大权限"三件套；
从属写路由表 + 示例 + 下一步说明的组合下发。**必须写清的边界**：平台侧"MCP 客户端缺失 / 单轮不可见 /
ACP 无发现"是对方实现限制，属**技术背景**而非本发明实施条件（`docs/mcp-binding.md` §5、§7）。

## 5. P12 框架自带受约束意图通道（自有 agent API 对接外部 LLM）

### 5.1 技术问题

两条极端都不能要：① 只依赖平台提供模型通道 ⇒ 平台无 key/无发现即全栈不可用；
② 让 LLM 输出直接驱动 ⇒ 违反"语言模型不得下发电机/关节命令"。
中间路线的真问题是**异构模型网关的能力差异**：实测某 OpenAI 兼容网关对 `response_format.type=json_schema`
直接返回 400（同一请求去掉该字段即 200），降级到弱约束后模型开始自创顶层键（返回 `{"type": "move_joint"}`）；
另有一次推理型模型把 256 token 全用在思考上（`finish_reason=length`、`content` 为空）。

### 5.2 机制

- S1 由框架内置意图提供者直连外部模型接口，**输入只有技能契约**（各技能输入 schema + 允许关节集合），
  输出被约束为**枚举化联合模式**：每个技能一个常量分支 + 一个"非机器人任务"分支（空技能 + 原因）。
- S2 请求层**降级链**（强 schema → 弱 JSON 对象 → 无格式约束），但**降级不放宽校验**：
  任何档位取得的文本都用同一份 schema 校验器复核，不合法即失败。
- S3 语义后校验：结构化参数里的关节名必须属于契约声明集合（拦截"把字段名当关节名"）。

- S5 意图结果**只**进入任务编排 → 技能管理 → 策略网关，永不产生控制量；温度与思考开关固定以保可复现。
- S6 "不是机器人任务"用**独立异常类型**表达，使上层能区分"过滤"与"解析坏了"。
