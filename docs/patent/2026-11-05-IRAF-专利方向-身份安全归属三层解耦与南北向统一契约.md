# IRAF 专利方向：机器人框架的"身份-安全-归属"三层解耦与南北向统一契约

日期：2026-11-05
范围：把原"方案 1（多调用方身份隔离）"丰富为一件可独立申请的发明，并与"方案 3（南北向统一契约）"
合并成一条更硬的独权。本文件是方向分析（四元组 + 权项要点 + 规避空间），供交底书选题用。

## 0. 发明锚点（一句话）

同一套机器人应用框架，在对外暴露任务级接口（北向 MCP）时，把"谁在调用（身份）"、
"能做什么（安全上限）"、"做了什么（执行归属）"三者显式解耦、各自独立闭环，
并把归属随 lease/fencing 贯穿跨机能力链（南向 Provider），最终回写到调用方名下。

## 1. 四元组

### 1.1 技术问题（换掉这段机制，功能是否还成立？不成立 ⇒ 是发明点）

机器人应用框架要对外交付（上位机 harness、第三方 Agent 平台、语音前端多方调用），
但传统做法把"身份"与"授权"绑死：
- token 即权限 ⇒ token 泄露即越权，且安全上限随 token 走（不是机器人自身的控制边界）；
- 身份不能独立撤销/轮换（一改 token 连带改权限）；
- "谁提交的任务"停在前端，无法贯穿到跨机执行面（x86 仿真 Provider / 客户 Provider），
  审计只能到"提交"这一步，查不到"谁让哪台机器人做了什么"；
- 多方共用一个框架时，进程级全局状态（robot_mode）互相污染，跨调用方串状态。

### 1.2 机制（三层解耦 + 南北向统一）

- 身份层（L1，OS 层）：身份只来自受信 transport（HTTP Bearer token / stdio env），
  token 注册表只存 SHA-256、文件 600、热加载撤销；请求体自报身份一律忽略。
- 安全层（L4，机器人层）：安全上限**只**来自签名 RobotProfile/SafetyPolicy；
  token 只回答"你是谁"，**不承载任何控制权限**，泄露/越权也动不了控制边界。
- 归属层（L5/L8，执行层）：执行（execution）绑定调用方 subject，查询按 subject 过滤
  （get_for_subject，他人 execution_id 返回 NOT_FOUND，不泄露存在性）；
  审计 JSONL 不含 token 明文/哈希。
- 多模式凭据隔离：上位机/AgentOS/Provider/模型网关四套凭据互不复用 + 状态按 subject 分桶。
- 南北向统一：南向 ProviderKit 复用与内置 Provider 相同的 provider.proto
  （Health/Invoke/Cancel + LeaseEnvelope），lease/fencing/幂等契约与北向一致，
  归属由此贯穿到跨机执行面。

### 1.3 技术效果（实测数字）

- 无 token/失效 token ⇒ 401；有效 token ⇒ 5 tools + skills=15；热撤销后同一 token 立即 401。
- 归属：A 提交 execution_id=287191a0-5cbc-...，B 的 token 读回 NOT_FOUND。
- 授权：只有 task.read 的 token 提交 ⇒ IRAF-POLICY-DENIED，无动作、无 execution_id。
- 失败关闭：缺注册表启动退出 2；INSECURE=1 绑 0.0.0.0 被拒。
- 51 项单测通过（test_mcp_auth / test_execution_store_ownership / test_sdk_mcp_adapter 等）。

### 1.4 与已申关系

- 与 P11（北向语义收口）互补：P11 锁"只暴露任务级工具 + 路由 + 过滤"，
  本方向锁"身份与安全解耦 + 归属贯穿 + 多模式隔离"，二者独权不同。
- 与 P9（跨机仿真 Provider）互补：P9 锁"控制面/执行面分离 + 执行域租约"，
  本方向锁"归属随 lease 贯穿到执行面并回写调用方"，可作为 P9 的从属或同日申请。
- 与 P10（装完 SDK 即有 Provider）互补：P10 锁"声明驱动服务固化"，
  本方向锁"南北向同一 lease/fencing 契约"。

## 2. 权项要点

独权（方法/系统）：
1. 一种机器人应用框架的多调用方安全控制方法，包括：
   a. 从受信 transport 获取调用方身份标识（token），仅用于标识调用方、不承载安全上限；
   b. 依据已签名的 RobotProfile 与 SafetyPolicy 判定所述调用方的允许操作，
      其中安全上限唯一来源于所述签名声明，与所述身份标识相互独立；
   c. 将所述身份标识绑定到执行记录，并随执行租约（lease）与围栏（fencing token）
      贯穿到跨机的执行面（能力 Provider）；
   d. 依据所述身份标识过滤执行查询，对非本调用方的执行标识返回不存在，不泄露存在性。

从属权项（可逐条加）：
- 身份标识注册表仅存摘要（SHA-256）、文件权限 600、按 (mtime,size,inode,ctime) 热加载撤销。
- 授权范围含 task.submit/task.read 两类 scope + resource_id 绑定。
- 多调用方共享状态按 subject 分桶（mode.state_for），stdio 单 subject。
- 四套外部身份（上位机/Agent 平台/能力 Provider/模型网关）凭据互不复用 + 模式分桶。
- 无注册表且未显式不安全开关时拒绝启动（失败关闭），不安全开关仅允许绑定回环。
- 审计日志不含 token 明文与摘要。
- 南向能力接口（ProviderKit）与内置 Provider 共用同一 provider.proto 及 LeaseEnvelope，
  lease/fencing/幂等契约一致。

## 3. 规避空间（竞争者如何绕过独权）

- 只做 Bearer token 鉴权，不拆"身份/安全"两层 ⇒ 规避 a+b；
- 只做审计日志，不把归属贯穿到跨机执行面 ⇒ 规避 c；
- 只做 OAuth scope，不以签名 Profile/Policy 作为唯一安全上限 ⇒ 规避 b；
- 只做多租户，不做"执行标识不存在性不泄露" ⇒ 规避 d；
- 南北向分开两套鉴权、不统一 lease/fencing ⇒ 规避南向从属。

⇒ 独权必须同时锁 a+b+c+d 四点，缺一即被绕开；这也是"三层解耦"比"单一身份隔离"硬的原因。

## 5. 诚实边界

- mTLS 客户端证书 CN 绑定、OAuth 2.1、限流未实现（ADR-0011 已声明）⇒ 交底书不得写成"已实现"。
- 全部为仿真/板上 HTTP 实测，不构成真机/实时能力证据（simulation=true）。
- "身份与授权解耦"是安全领域已知原则；本方向的新增贡献必须落在
  "机器人上下文的三层显式解耦 + 归属跨机贯穿 + 南北向统一契约"这个组合上，不能单写"身份隔离"。
