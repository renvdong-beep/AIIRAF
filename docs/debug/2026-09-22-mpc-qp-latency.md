## 3. 从它的源码读出的三条事实（决定口径，非推测）

证据文件：`build/research/mpc-repo/examples/examples__ex02_trot_forward.py`（行号即该文件行号）

1. **它的实际 MPC 更新率是 50 Hz，不是 48 Hz**
   - L65 `CTRL_HZ = 200`（控制拍 5 ms）；L79 `MPC_DT = GAIT_T / 16`；L80 `MPC_HZ = 1.0 / MPC_DT`；
     L81 `STEPS_PER_MPC = max(1, int(CTRL_HZ // MPC_HZ))`
   - ⇒ `int(200 // 48.0) = 4`（向下取整）；L217 `if (ctrl_i % STEPS_PER_MPC) == 0` 才求解
   - ⇒ 实际更新间隔 = 5 ms × 4 = **20.0 ms = 50.0 Hz**。
   - README L118 的"48 Hz real-time budget (20.8 ms)"是把 `MPC_DT = GAIT_T/16 = 0.0208333 s`
     画成图上的预算线（L316 `plot_solve_time(..., MPC_DT, MPC_HZ, ...)`），**不是**代码执行的周期。
2. **它的求解在控制拍内联、且主循环无实时节拍同步**
   - L203-231：MPC 求解在控制拍分支内联（阻塞该拍）；L199-306 全文无 sleep/同步，
     `mj_step` 每步固定推进 1 ms 仿真时间。
   - ⇒ 求解耗时在它那边表现为"仿真时间落后于墙钟"，**不构成 deadline 违约的观测**。
     照抄该结构到我们的 100 Hz 闭环 = 违反铁律 4 与 ADR-0009 §4.3/§4.4（重计算不得进实时闭环）。
3. **参考相位按实测时间推进**（L200 `time_now_s = float(mujoco_go2.data.time)`；
   L220-229 用 `time_now_s` 调 `generate_traj`，`time_step=MPC_DT` 只作为 MPC 内部离散化步长）
   - ⇒ 声明步频 3.0 Hz 精确成立，不随线程周期漂；`MPC_DT` 与线程周期的 4.17% 差异（20.8333 vs 20.0）
     是**它的实现事实**（L68-73 注释声称"clean decimation"但 200/48 = 4.1667 非整数），不是我们的缺陷。

## 4. 口径决策（本文即准；ADR-0009 §6.5 同文）

- **解耦口径**：MPC 独立进程/线程，更新周期 **20.0 ms（50 Hz）**，对齐声明的
  `control_frequency_hz = 100`（`profiles/unitree_go2_mujoco.yaml:12`）⇒ 每 2 拍更新一次；
  **不**与关节控制 100 Hz 同步、**不**在控制拍内联求解。
- **预算取值 = 20.0 ms**（不是 20.8333）：14.102 / 20.0 = **70.51%**（比它 README 口径 67.69% 更严）。
- **MPC 内部 dt 保持 `GAIT_T/16 = 0.0208333 s`**：16 × 0.0208333 = 0.333333 s = GAIT_T（整除是接触表相位的前提；
  改成 0.02 得 16 × 0.02 = 0.32 ≠ GAIT_T，每个 horizon 相位漂 13.33 ms）。
  参考相位按**实测时间**推进（同它 ex02）。
- **否决 100 Hz 同步支**：(a) 实测 141.02%，非口径可救；(b) 与铁律 4、ADR-0009 §4.3/§4.4 冲突。
- **新鲜度门禁**：解龄 > 2 个 MPC 周期（> 40.0 ms）即 `damped_hold`；QP 无解/超时同样走显式失败路径
  （移动中 `damped_hold`，急停 `torque_zero_release`）；不得降级为"继续跑旧解"（ADR-0009 §4.3）。

## 5. 判据（可测，事后不改）

① **通过** ⇔ 下列三条同时成立（≥2000 次连续求解、预热样本剔除后）：
1. 整步墙钟 **P99 ≤ 15.0 ms**（= 0.75 × 20.0 ms 预算）
2. 超时次数（整步墙钟 > 20.0 ms）= **0**
3. 稳态样本内 **max ≤ 20.0 ms**

现状：条件 1 成立（P99 14.102 ms = 70.51%）；**条件 2/3 未判** —— 200 次样本 max = 19.965 ms
= **99.825% × 20.0 ms**（= 95.832% × 20.8333），距越界 0.035 ms。

## 6. 必补测量（不改阈值与判据，只把口径包对）

1. **冷启动归属**：分离 CasADi 函数编译 / OSQP 工作区分配 / 对偶预热（`lam_a_prev`）等一次性开销
   （先预热约 20 次再计时），dump 最慢 10 个样本的 index。
   - max 落在前几次 ⇒ 条件 3 成立，且实现里预热必须放进 init 并记录启动序列；
   - max 落在稳态样本 ⇒ ① **不通过**，按 ADR-0009 收口。
2. **计时器包边界**：现脚本墙钟只包 `mpc.solve_QP`（`traj.generate_traj` 在 start 之前）。真实每拍
   计算量 = `generate_traj` + `solve_QP`。由现有数据反推该项：mean 差 = 11.893 − 10.078 = **1.815 ms**、
   P99 差 = 14.102 − 12.267 = **1.835 ms**，目前**未进预算**。补测：计时器包住整个 MPC 计算体
   （generate_traj + solve_QP + 时间戳打标），阈值不动，重出 P50/P95/P99/max。
3. **迁移性**：x86_64 结果只判"可继续"，不判"可上线"；① 的最终证据必须来自目标 aarch64
   （`casadi` / `pinocchio` 的 aarch64 wheel 已在 ADR-0009 §4.1 核实可下载），并在 BoardProfile 登记
   `casadi` / `osqp` / `numpy` 版本（本机 `mpc-env/` 同时存在 `numpy-1.26.4` 与 `numpy-2.2.6` 的 dist-info，
   `osqp 1.1.3`）。

- **GC 归因不成立（证据反而相反）**：两轮稳态窗口内 **gen2 collection = 0、gen0 仅 3/0 次**，
  2 个尖峰与任何 collection 都**不重合**；关闭 GC 后尖峰消失（2 → 0），但尖峰位置在两轮之间本就不同
  （#1243/#1282/#1320 vs #1398/#1435）⇒ 2 次 vs 0 次属**样本量不足的噪声差**，不足以归因到 GC。
  关闭 GC 只削掉了尾部（wall_step P99.9 36.645 → 21.274、max 69.532 → 26.067），**中位数毫无改善**
  （P50 16.853 → 16.816）。
- **稳定复现的是"地板"，不是尖峰**：三轮独立运行的中位数与 P99 高度一致 ——
  wall_step P50 **16.899 / 16.853 / 16.816**、P99 **18.911 / 18.452 / 18.571**，
  即每拍 ≈ **16.8 ms = 预算的 84%**（占空比），P99 ≈ **92.6~94.6%**。越界 4~9 次 / 2000 次，三轮均非零。
- **成本构成（P50）**：`update` 1.706 + `solve` 10.001 + `gen_traj` 4.730 ≈ 16.44 ms（+ CasADi 调用开销 ≈ 16.9）。
  即 **QP 求解段占 59%、参考轨迹生成占 28%、矩阵更新占 10%**。

**E. ① 的结论**：**不通过**（§5 三条判据全部不满足，且属"地板"层面不满足，非尾部噪声）。
失败**不可**通过调整口径消除：把 `gen_traj` 移出计时范围正是本补测要禁止的动作（它每拍真实发生）。
另注：那 3 个 >40 ms（= 2 个 MPC 周期）的尖峰若出现在闭环里，会触发新鲜度门禁 ⇒ `damped_hold`，
故"解耦"本身不提供尾部保护。

**F. 与作者数字的偏差定位（本轮新增）**：README "模型更新 ≈1.03 ms / QP ≈1.67 ms" 对照本机
`update` P50 **1.706 ms**（1.66 倍）与 `solve` P50 **10.001 ms**（**5.99 倍**）
⇒ 模型与矩阵构建这一段与其同量级，偏差**集中在 QP 求解段**。本机求解器栈：`casadi 3.8.1`
（`ca.conic('S','osqp',...)`）+ **`osqp 1.1.3`**（`osqp/ext_builtin...so`）+ `numpy 2.2.6`/`1.26.4` 并存
+ `scipy 1.15.3`；对方走 conda-forge `osqp`（版本未在 README 声明）⇒ **版本/设置差异是待验证假设，不是结论**。

### 11.2 原生 OSQP 重放（真实连续 200 个 QP；决定性）

方法：代理截获 `solve_QP` 每次交给 CasADi 的真实 `h/g/a/lba/uba/lbx/ubx`，
按 OSQP 约定重建 `P`（本问题纯对角，nnz = 384）、`A_full = [I; A]`（832×384）、`l/u` 拼接，
逐样本 `setup → warm_start(上次的 x,y) → solve`，并与**同一批** CasADi 的 `solve_time` 对比。

```
CasADi solve_time（同批 200 个 QP）：P50 10.0158 ｜ P90 11.6219 ｜ P99 11.8614 ｜ max 11.9434 ms
原生 + setup + warm_start(上次)：setup P50 1.5432 ｜ solve P50  9.5928 ｜ total P50 11.1586 ｜ iter P50 325
原生 + setup + 无热启动（对照）：                              solve P50 14.4013 ｜ total P50 15.9436 ｜ iter P50 505
原生 + warm_start + eps 1e-3：                                solve P50  5.5471 ｜ total P50  7.1003 ｜ iter P50 190
⇒ CasADi / 原生(纯 solve) = 1.04 倍；CasADi / 原生(含 setup) = 0.90 倍
```
（`r2_native_osqp.py` 里"同一 QP 反复热启动"得到 iter P50 = 10、solve P50 = 0.2379 ms —— 那是
**同一个 QP**，热启动解已在最优点上 ⇒ 方法学上不公平，仅作对照，不作为结论。）

**结论（求解器分支）**：瓶颈**不在 CasADi 接口层**（比值 1.04），**也不在 CPU**，而在
**OSQP 1.1.3 对这批 QP 的收敛**：热启动后仍需 **325** 次迭代（对比"QP 不变"时的 10 次），
冷启动 505 次。机制（可解释，不是猜测）：代价矩阵 `R = 1e-5·I`、`Q = diag([1,1,50,10,20,1,2,2,1,1,1,1])`
⇒ `H = 2·diag(Q,R)` 的对角元素跨度 **2×50 = 100 到 2×1e-5 = 2e-5（比例 5×10⁶）**，
而 OSQP 是一阶（ADMM）法 ⇒ 病态 + 近退化的输入代价必然吃迭代。作者 README 的 1.67 ms 与本机
9.59 ms 的差异，机制上指向 **版本/默认设置不同**（本机 osqp 1.1.3；其 `environment.yml` 走 conda-forge
且未声明版本），但**仍未证实**。

### 11.3 质量口径的一处修正（诚实标注）

v2 扫描用"首步 GRF 与 baseline 的 `Δu/‖u‖`"作质量指标，发现**同一指标对几乎任何微扰都给出 ~24%**
（仅 `scaling=10` 为 0）。原因是 `R = 1e-5` 使**力解近退化**：许多力分布在代价上近乎等价，
解对求解路径极度敏感 ⇒ **首步 GRF 不是可用的质量指标**。
⇒ 质量判据必须用**闭环判据**（②③ 的速度跟踪误差、倾角上界、接触力上界），不能用开环力向量对比。

## 13. R2 · 等价预条件（变量缩放）：**成立**（2026-09-22）

脚本：`build/research/mpc-repo/r2_preconditioning.py`（原生 OSQP，重放真实连续 200 个 QP）。

## 25. 单变量闭合：决定性的初始化差异是"初始条件"而非设置顺序（2026-09-22）

| 变体 | 与它 ex02 的比对结果 |
|---|---|
| 原版（x0=0，`timestep` 在 `update_with_q_pin` 之前） | 第 1 拍起分叉（Δz 1.239e-05）⇒ 最终跌倒 |
| 改两处（x0=−5，`timestep` 挪到之后） | **1000 拍 0 处发散**（容差 1e-6） |
| **只保留 x0=−5、把 `timestep` 挪回之前**（本轮单变量） | **1000 拍 0 处发散**（z 末值 0.2823、倾角 max 3.90° 与它 ex02 完全相同） |

⇒ **`timestep` 的设置顺序无关**；决定性的是**初始条件逐字复刻**（`INITIAL_X_POS = −5`）。

**含义（对实现有直接价值）**：两边都从"足端沉入支撑面 **18.372 mm**"的初始条件起跑，初始接触冲量极大、
仿真对该瞬态处于**浮点舍入级敏感**（5 m 的 x 位移差就足以改变舍入序列 ⇒ 1e-5 级分叉 ⇒ 1.5 s 后跌倒）。
因此：
1. 我之前的 ②③ 数字确实是探针缺陷所致（初始条件未复刻），**作废成立**；
2. **对我们自己的接入更重要的结论**：**不要**让机器人从"足端穿透支撑面"起跑。我们框架的
   `initial_alignment`（抬到刚好接触，实测 0.018372500 m、对齐后足端间隙 2.082e-17 m）
   正是消除这个病态瞬态的做法——**②③ 的稳定结果是在这一前提下取得的**，这条必须作为接入要求写进
   `adapters/` 的实现与验收场景（不是可选项）。
