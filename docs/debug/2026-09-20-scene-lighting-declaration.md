# 2026-09-20 场景光源声明化：从"接近全黑"到可读

## 1. 现象与量测

在 Viewer 里看 UR5e / Piper 抓取时，用户问"有没有颜色"。离屏相机渲染的像素统计：

```
改动前：UR5e 均值 RGB (23.6, 23.8, 25.7)   64.5% 像素≈(16,16,16)
        Piper 均值 RGB (14.2, 15.8, 18.1)   98.1% 像素≈(16,16,16)
```

即：画面有颜色但整体接近全黑。检测器仍能工作（颜色分割按色调判据、不依赖亮度），
但人眼与证据截图不可读 —— 这正是用户此前反馈过的"MuJoCo 太暗"。

根因：**两个场景生成器都不处理光源**，配置里也没有光源声明。
Piper 场景 0 个 `<light>`，UR5e 只有官方模型自带的 1 个（无补光、无背光）。

## 2. 改法（声明式注入，跨机型可移植）

- 新增 `src/iraf_adapters/mujoco/scene_lighting.py`：按 `scene.lights` 向
  `<worldbody>` 注入 `<light>`；字段与取值显式校验（dir 不得为零向量、
  diffuse/specular 非负有限、未知字段即失败）；**未声明则不注入**（保持既有行为）。
- 两个场景生成器各加一行调用，光源成为配置文件里的数据，不在代码里。
- 两台机型的 `config/*_simulation_baseline.yaml` 声明同一组**方向光**
  （方向光与工作空间位置无关，因此跨机型复用同一份声明）：
  key（近垂直主光）+ fill（侧补光）+ rim（背光）。

## 3. 踩到的坑：光照会破坏颜色分割（重要）

第一版用"斜射主光 + 阴影"，结果 **UR5e 视觉验收直接失败**：

```
ValueError: 目标 box_01 尺寸校验失败: fitted=[0.077636, 0.03927] expected=0.050000
```

链式原因（两步）：

1. `castshadow: true` 的阴影把台面染成与目标相近的色调 → 颜色掩码被放大；
2. 更本质的是：**侧面被照亮后也落进颜色阈值**，位姿拟合的"最大支撑平面"
   从顶面变成了侧面（顶视相机 + 斜射光 = 侧面在图像里更大），
   拟合矩形因此变成 1.55 倍。

结论与做法：主光改为**近垂直**（顶面受光充足、侧面掠射很暗），阴影默认关闭。
这既让画面可读，又让"顶面主导"的假设继续成立。

> 教训：**渲染颜色是检测链路的输入**。改光源/材质/相机等于改检测输入，
> 必须重跑视觉验收 —— 本次正是靠重跑验收当场发现，而不是等真机抓偏了才查。

## 6. 后续查明：抬升位移变化的真因是配置被静默删键（已修复并加门禁）

"改光源"时为了替换 lights 块，用"从 `lights:` 截到下一个空行"的文本替换写回配置 ——
结果把 `scene:` 段**在 lights 之后的其它键整段删掉**：

| 机型 | 被误删的 scene 键 |
| --- | --- |
| UR5e | `timestep_s`、`gravity`、`pad_friction`、`camera`、`inject_arm_position_gains` |
| Piper | `timestep_s`、`gravity`、`finger_friction`、`arm_position_kp`、`camera`（整段） |

代价（实测，UR5e）：

```
pad_friction 丢失 → 夹爪接触力 17.451911/16.053349 N → 8.840401/8.863601 N（约一半）
                    抬升位移      0.041208 m        → 0.050928 m
所有门禁仍然"通过" —— 因为容差宽松，静默降级不会报错
```

定位方式：连跑 3 次验收（结果逐位相同 → 排除随机性）→ 用**结构化对比**
（两个 git 版本的 YAML 解析后逐键比对）找出被删的键（行尾变化会让文本 diff 变成
整文件重写，看不出删键）。

修复与验证：

```
从 85d0073 恢复两台机型的 scene 物理键（并保留新增的 lights）
重建 + 重跑四条验收：
  UR5e 力 17.451911/16.053349 N、抬升 0.041208 m  ← 逐位回到原值
  Piper 0.240676/0.244112 N、抬升 0.087184 m、偏差 0.002826042685491991（不变）
```

新增门禁（`scripts/profile_check.py` 第 6 项）：**场景物理参数必须显式声明且真的生效** ——

- 缺 `timestep_s` / `gravity` / 指腹摩擦声明 → 失败（防"静默回落默认值"）；
- 已生成场景时，比对 `model.opt.timestep` / `model.opt.gravity` /
  指腹 geom 的 `geom_friction` 与声明是否一致 → 失败（防"声明了没生效"）。

负向验证：把 `pad_friction` 从配置里删掉后，`profile_check` 报
`基线 scene 段缺少 None（指腹摩擦）：场景会静默回落到模型默认值，实测会让夹持力/抬升位移变化而不报错`。

教训：**"通过"不等于"正确"** —— 门禁只覆盖它检查的维度；凡是"声明缺失就回落默认值"
的参数，都必须显式声明并被门禁核对是否真的生效。
